# 開発ルール

## プロジェクト概要

スポーツ施設のWeb予約・概算見積もりシステム。

- 利用者がWeb上で施設を予約し、料金の概算見積もりを確認できるようにする
- GitHub Pages で公開する。ルートの `index.html` がツール一覧のポータル画面
- ツールは英数字のフォルダに `index.html` として置く（例：`estimate/index.html` が概算見積もりツール）。URL に日本語を入れない
- テストは `node --test "tests/**/*.test.js"` ですべて実行する

## Gitルール

- **mainブランチを直接編集しない**
- **作業ごとにブランチを作る**（例：`feature-xxx`、`fix-xxx`、`docs-xxx`）
- **コミットは小さく、こまめに**、メッセージは**日本語**で書く
- **rebaseは使わない**。ブランチの取り込みには `merge` を使う（例：`git merge --no-ff <branch>`）
- **実装のコミットとリファクタリングのコミットを分ける**
  - 機能追加・修正のコミットに、動作を変えない整理（リファクタリング）を混ぜない
  - リファクタリングだけのコミットは、メッセージにその旨を書く（例：「リファクタリング: 料金計算処理を関数に分割」）
- `Claudeのキー.txt` などの秘密情報は絶対にコミットしない（`.gitignore` で除外済み）

## 特定防止ルール

- **特定防止のため、固有名詞・実在の地名・公的機関名をコードやテストに含めない**
- 名前が必要なときは、**一般的な民間企業風のダミー名**を使う（例：株式会社サンプルリゾート、あおぞらセミナーハウス、山田 太郎）
- 実名で表示したいときは、Git管理外の `facility-config.js`（`window.CUSTOM_FACILITY_INFO`）に書く（`.gitignore` で除外済み）
- コミットメッセージ・仕様書（`SPEC.md`）・ブランチ名にも実名を書かない

## コード品質基準

- **1つの関数は10行以下**を目安にする（長くても1画面に収める）
- **`const` を基本にする**。変数の再代入（上書き）はしない
  - `let` / `var` は使わない
  - 値を変えたいときは、新しい変数や新しいオブジェクト・配列を作る
- **純粋な関数にする**
  - 同じ入力には必ず同じ出力を返す
  - グローバル変数や外部の状態に頼らず、必要な値は引数で受け取る
  - DOM操作などの副作用は、計算の処理と分けて最小限にする
- **関数どうしの依存を減らす**
- **役割がひと目でわかる名前をつける**
  - 関数名は動詞から始める（例：`calculateTotalPrice`、`formatReservationDate`）
  - 変数名は中身がわかる名詞にする（例：`hourlyRate`、`reservationList`）
  - `data`、`tmp`、`x` のような意味のあいまいな名前は使わない

## テスト方針

- **機能を実装するときは、動作確認用のテストコードも一緒に書く**
- 純粋な関数は、入力と期待する出力の組み合わせでテストする
- 境界値（0、上限、空の入力など）や異常系のケースも確認する
- テストは実装と同じコミットに含める
